03 · History
Four eras of AI
▼

Lobel's framing device for the whole morning. Each era did not replace the last — the earlier ones are still doing most of the paid work in industry.

  1. Traditional supervised learning — demand forecasting, credit scoring. 50+ years old and still very useful. This is most of what Bapna taught on Days 1–3.
  2. Deep learning — kicked off in 2012 with AlexNet (Geoff Hinton's team, Ilya Sutskever among them), which won ImageNet by separating cats from dogs in photographs — a task previously considered impossible.
  3. Generative AI — the ChatGPT moment, November 2022. The machine generates language and images and holds a conversation.
  4. Agentic AI — the current era and another step change. Agents understand intent, plan, and execute autonomously rather than answering one question at a time.
The point of the ladder

Each step moved the unit of work up: from a prediction, to a perception, to a paragraph, to a task. The project you are building lives on step four, but nothing stops you from putting a step-one model inside it.

The competitive landscape
▼

Where the money is

  • Anthropic revenue is now roughly 2× OpenAI's, and Anthropic is reportedly targeting a $2T IPO valuation; OpenAI is valued around $1T.
  • Anthropic's inflection point was Claude's coding agent going viral in Dec 2025 — the moment agents stopped being theoretical.

Straight out of Clay Christensen. Google had the research and the talent and did not ship a chatbot, because a chatbot cannibalizes sponsored-search ad revenue — the thing paying for everything else. DeepSeek, Qwen, Kimi, Minimax — genuinely strong competitors and significantly cheaper to run. How the machine actually works
🎲
06 · Mechanism
Next-token prediction, and what follows from it
▼

A token is roughly a word — sometimes half a word. Given a sequence of tokens, the model produces the most probable next token, then the next, then the next. Each one comes off a probability distribution:

The distribution

“Donald …” → “Trump” 62% · “elected” 22% · a long tail of everything else. Training a model means learning these distributions across the entire internet. That is the whole trick.

Three properties that fall straight out of the mechanism

Probabilistic The same input can produce a different output every run — fundamentally unlike traditional software, where identical input always gives identical output. This is the same property that gives you creativity and that gives you hallucination. You cannot keep one and delete the other.
Frozen at training No knowledge of anything after the training cutoff. Trained in March, released in July → it knows nothing about the World Cup that happened in between. This is why tools exist.
Confident when wrong Because it is only ever picking the most probable next word, it sounds exactly as authoritative when hallucinating as when correct. There is no internal tell for you to read.
Carry this into the project

Every design decision downstream — orchestration, the 2×2, human-in-the-loop, evaluation — exists to manage these three properties. If you understand this card, the rest of the day is consequences.

🌡️
07 · Knob
Temperature — and the knob that replaced it
▼

Temperature controls how random the output is by reshaping the probability distribution before sampling.

High · 1.0 Flattens the distribution — unlikely tokens become more probable. More creative, more hallucination.
Low · 0.0 Collapses to 100% on the top token every time. Deterministic, predictable, dull, less hallucination.

The history of the knob

  • Default was 0.7 in GPT models up through GPT-4, and users could set it explicitly.
  • Modern models (Claude, newer GPT) no longer expose temperature as a user-facing control — the providers tune it internally.
  • In n8n, with older models, you can still set it and experiment. Worth doing once just to watch the output loosen.
What replaced it

The control you now have is how much thinking to apply — instant / medium / high / very high / pro in ChatGPT. That is a proxy for how many tokens the model spends planning and verifying before it answers. Temperature tuned the sampling; the thinking dial tunes the effort.

🧠
08 · Sizing
Model sizes — and which one to build with
▼

The names are sizes of neural network, not different products. Haiku / Sonnet / Opus for Claude; mini / standard / o-series for OpenAI.

Larger More expensive per token, slower, more capable.
Smaller Cheaper, faster, and good enough for essentially everything in this class.
For the build

Use GPT-4o-mini or Gemini Flash. Big reasoning models like o3 are too slow for iterative building — you will be running the same workflow forty times, and a 30-second round trip turns an afternoon into a week.

From a language model to an agent
🔧
09 · Anatomy
The three additions that make an agent
▼

An agent is not a different kind of model. It is the same next-token machine with three extra token types that let it act.

  1. Reasoning tokens. A special token tells the model to think silently first — it generates internal “scratch paper” that is never shown to you, reasons through the problem, then answers. Not a different model — the same model, with a token that shifts the distribution toward reasoning-style text.
  2. Tool calls. A token triggers an external action — read email, query a database, run a Python script, hit an API. The result is injected back into the token sequence and generation continues as if it had always been there.
  3. Subagents. A token spawns a specialized child agent. The child runs its task and feeds results back to the parent. This is what buys you parallelism and specialization.
Why reasoning traces are hidden

Companies hide the reasoning trace to prevent distillation — a competitor training a cheaper model on your model's own thinking. The trace is the most valuable output, so you never see it.

♾️
10 · Loop
The agentic loop
▼
Three years ago You write a prompt → you get a response → you iterate. The human is the loop.
Now You give a goal → the agent plans → executes with tools → verifies the output → loops back if verification fails. The human sets the objective and inspects the result.

The thinking dial in ChatGPT (instant → pro) is really a dial on how long the agent spends in the planning and verification phases of that loop.

Design consequence

Verification is a step in the loop, not an afterthought. If your agent has no way to check its own output, the loop has no exit condition except “it produced something.”

11 · Framing
AI project vs. AI process
▼

Lobel's stated goal for the day: shift your mental model from AI projects to AI processes.

AI projectAI process
ShapeOne-offAlways on
StartsYou open ChatGPT and askA trigger (new email) or a schedule (every morning)

ValueSaves you an hourWhere the economic value is
Why it matters beyond the class

The stock market and enterprise investment are pricing AI processes, not one-off projects. A chatbot someone has to remember to open is not an operating change; a thing that fires on every inbound email is.

Project implication

Your deliverable is a website with an agent behind it — which is a project shape. The way to score on component 1 is to make the case that it sits inside a process: what triggers it, how often, and what happens to the output.

12 · Lever
Orchestration — the dial you actually control
▼

Orchestration = how much structure you impose on the agent's sequence of steps, versus how much freedom you hand the LLM.

More orchestration More predictable. Better at managing stochasticity. Looks like traditional code: do this, then this, then that.
Less orchestration More flexible. Better at novel situations. The LLM figures it out.

Real systems are a combination — some rule-based structure, some LLM interpretation.

The one-liner

Orchestration is the key lever for managing the probabilistic nature of LLMs in production. When your agent misbehaves, the first question is not “which model?” — it is “which of these steps should I have taken away from it?”

13 · Framework
The 2×2 — when to use an agent at all
▼

Axes: cost of error (low ↔ high) × ambiguity (low ↔ high).

Low cost of errorHigh cost of error
High ambiguityAgent sweet spot — complex, open-ended tasks where mistakes are survivableHuman in the loop — agent interprets, human decides
Low ambiguityTraditional automation — vending-machine logic, no LLM neededDeterministic software with strict rules
Use it as a filter, not decoration

Two of the four boxes say do not build an agent. Running your project idea through this honestly is free marks on component 1 — and if your idea lands bottom-left, an LLM is the wrong tool and you should pick another idea today rather than in September.

15 · Build
The core workflow — a chat agent in seven steps
▼
  1. New workflow → the plus button → add an AI Agent node.
  2. The AI Agent node has three connection points: chat model (the LLM), memory, and tools. Everything today hangs off those three.
  3. Add a chat model — Gemini Flash or GPT-4o-mini, with your API credential; pick the model from the dropdown.
  4. Open the chat and test something trivial: “my favorite color is red.”
  5. Observe the failure: with no memory node attached, the agent does not remember the previous message. This is not a bug — it is the default.
  6. Add a Simple Memory node, context size 5 (it keeps the last five messages), and connect it. Test recall.
  7. Add a system prompt — double-click the AI Agent node → Options → Add System Message.
The system prompt is the whole ballgame

It is the most important configuration in the node, and n8n buries it under Options. Write plain English: who the agent is, what it should do, what it must never do, and the tone or persona. The class test case was “you are my pirate assistant, speak like a pirate” — deliberately silly, because you want an unmistakable signal that the prompt is being applied.

Subtlety worth knowing

The system prompt is sent to the LLM on every message, but it is not stored in the simple memory. Memory holds the conversation; the system prompt is re-attached each turn.

🧵
16 · Mechanism
How memory actually works under the hood
▼

This is the card that changes how you debug everything else.

  • Every new message ships the entire conversation history to the LLM as context.
  • Each call may land on a completely different server — different data centre, different chip.
  • So it feels like a conversation and is actually a series of independent one-shot calls, each with the full history prepended.
Why context windows are the spec everyone quotes

Because the whole conversation is re-sent every single time. That is the real cost driver, and the real constraint.

Practical consequences in n8n

  • Memory set to 5: send the 6th message and the oldest is dropped.
  • Even with memory set to 1, the agent seems to retain more — because its own previous answer contains references to earlier content. Context leaks forward through the model's own text.
  • Use the Reset button between tests. Otherwise old context bleeds into the next run and you will debug a ghost.
🌦️
17 · Tools
First tool — OpenWeather, and the fairy dust
▼
  1. Click the plus on the Tools connection of the AI Agent node.
  2. Search OpenWeather; add your OpenWeather API credential.
  3. Choose Current Weather; pick Imperial or Metric.
  4. Set the city field to an expression — the sparkle / “fairy dust” icon. This is the move: it tells the agent to work the city out from the user's message instead of you hardcoding one.
  5. Test: “What is the weather in New York City?”
Read the execution log — this is the lesson

agent → memory (retrieve) → LLM → OpenWeather tool → memory (store) → LLM again to formulate the response. Memory is touched twice — once to load context, once to save the exchange — and the LLM is called twice: once to decide to use the tool, once to write the answer using the result.

Expression fields are the difference between a tool and a setting

A hardcoded field is configuration. An expression field is a parameter the agent gets to choose, which is what makes the tool usable across arbitrary requests.

📅
18 · Tools
Google Calendar — four operations, one prompt
▼

The centrepiece build. Four separate tool nodes on the same agent, one per operation.

  1. Create — Google Calendar tool, operation Create. Connect Google credentials. Set Summary, Description, Location to expressions, and Start and End to expressions too.
  2. Get Many — retrieve events between now and one week out.
  3. Delete — set Event ID to an expression.
  4. Update — Summary, Description, Location, Start time and End time all as expressions.
The failure everyone hits

Omit Start and End from the Update tool and the agent cannot change event times — so it will silently do the next best thing it can: delete the event and recreate it. It looks like it worked. It is not what you asked for, and on a real calendar it destroys the invite and the attendee list.

Then go back and rewrite the system prompt

Explicitly list all four tools — add, get many, delete, update — and what each one is for. This significantly improves tool-selection accuracy. The agent is choosing from a menu; a menu with descriptions beats a menu of function names.

The test that proves it

“Move basketball from 6–7 PM to 7–8 PM and add NYU Gym as the location.” → the agent correctly calls Update with new times and the location, instead of delete-and-recreate.

19 · Debugging
The four mistakes he flagged by name
▼
Prompt in the wrong box Putting the system prompt in the agent node's prompt input field instead of the system message under Options. That field replaces the user's chat input rather than augmenting it — so the agent ignores the conversation entirely and answers your instructions instead.
Update without times No Start/End on the Update calendar tool → agent falls back to delete + create.
Dirty memory Not resetting memory between tests → old conversation context bleeds into new tests and you chase a bug that is not there.
Test URL in production Using the test webhook URL instead of the production URL when wiring Lovable. The test URL only listens while you have the n8n editor open and armed.
🔌
20 · Deploy
Swapping the chat trigger for a webhook
▼

To put a real website in front of the agent, the chat trigger has to go.

  1. Delete the Chat Trigger node.
  2. Add a Webhook node. Method POST. Response mode: Respond Using “Respond to Webhook” — so a downstream node returns the answer, not the webhook node itself.
  3. Add a Respond to Webhook node at the end of the workflow, set to First Incoming Item.
  4. AI Agent node: change input from Get from Chat Trigger to Define Below, and pass $json — the full JSON from the webhook — to the agent.
  5. Simple Memory node: change the session key to Define Below and set a fixed session identifier. That is fine for a single-user site; multi-user needs a unique key per user or everyone shares one conversation.
Stop here

Do not publish yet. The next card is not optional.

🔒
21 · Security
Header auth — the step you cannot skip
▼

An unauthenticated webhook is a public URL that spends your API credit and touches your calendar. Anyone who finds it can use it.

  1. Webhook node → Authentication → Header Auth.
  2. Create a Header Auth credential: Name = password, Value = a password you will remember — you have to type it into the website later.
  3. Now only requests carrying the correct header can trigger the agent.
Design note

This is a shared secret, not a user system. It stops drive-by use of your endpoint; it does not give you per-user identity. For the project that is the right amount of security — for anything real, it is not.

22 · Frontend
Building the site in Lovable
▼
  1. Log into Lovable. The corporate account gives 5 free daily credits + 25 monthly; a free personal account gives 5 daily.
  2. Copy the production webhook URL out of n8n — not the test URL.
  3. Prompt Lovable in plain English: what the site is for, paste the webhook URL, specify POST, specify Header Auth with name password, and instruct it to ask the user for the password and pass it as a header.
  4. Do not hardcode the password in the Lovable prompt. The frontend should collect it at runtime from the user. The frontend itself should never know the password value — anything in the frontend is readable by anyone who opens the page.
  5. Lovable builds in 2–3 minutes and will flag security warnings if the auth handling is ambiguous.
  6. Publish, name the site (his demo: BotCalMagic). Lovable runs a security check before publishing.
  7. Visit the live site, enter the password, talk to your calendar.
Shared workspace — read this

The class shares one n8n workspace and one Lovable workspace, built like a company account where all employees see each other's projects. Published Lovable sites are public by default — anyone with the URL sees the login page, anyone with the password gets the agent. Turn off cross-project sharing in Lovable settings if you do not want classmates in your project. Unpublishing takes the site offline; the n8n workflow keeps existing.

23 · Risk
Vibecoding security — two real incidents
▼

Lovable is built for people who are not engineers, and that is exactly what creates the exposure at scale.

Incident A women's safety app built on Lovable stored government ID photos behind an insecure webhook — anyone with the URL could download all of them.
Incident A single line of Python could pull all SQL records — including PII — out of insecure Lovable sites.

The distinction that matters: prototyping and experimenting, as in this class, is fine. Deploying at scale with real user data requires a real security review. Lovable's flagging has improved a lot in the last six months and still should not be trusted for sensitive deployments.

His closing line on it

“With great power comes great responsibility.” Vibecoding is a superpower; be careful before you put real users behind it.

24 · Method
Design first — the framework, not the tools
▼

Most people start by mapping the workflow or picking tools. That is backwards. Start from product design thinking, not from the agent's point of view.

The example that lands it

Read email vs. write email. Same inbox, same model, same tooling — and completely different risk profiles. One is reversible and private; the other is irreversible and goes to another human being. You cannot see that difference from the workflow diagram. You can only see it from the user's side.

Required

The Agent Design Worksheet from Lecture 2 is required reading and gets submitted as part of the project. Nine sections: objective, scenarios, features, tools, workflow, constraints, failure modes, persona, system prompt — everything you should have settled before opening n8n.

🤝
25 · Archetypes
Automation vs. augmentation vs. hybrid
▼
Automated AI decides end to end, no human in the loop. Good for low cost of error, repetitive work, and output that is easy to verify.
Augmented AI drafts or assists; the human makes every decision. Good for creative work, high ambiguity, and output that is hard to verify.
Hybrid Automated for the clear cases, human review for the edges. Credit-card approval is the canonical shape: auto-approve low risk, auto-decline high risk, route the middle band to a human.

The human in the loop plays two roles at once

RoleWhat it buys / costs
GuardrailAccountability and ethics. A person can be held responsible and can be fired. An AI cannot be fired.
BottleneckHumans are slow. Send too much to review and the queue piles up and the whole benefit evaporates.
The tension is the design problem

Guardrail vs. bottleneck. Every human-in-the-loop decision is a trade between the two, and “send everything to a human” is not a safe answer — it is a broken process wearing a safety jacket.

✅
26 · Test
Three criteria for good automation
▼
  1. Low cost of error — mistakes are cheap and recoverable.
  2. Good, clean data — tacit knowledge or dirty data makes automation unreliable.
  3. Easy to verify — you can tell, cheaply, whether the output was right.
Why coding and math went first

Correctness is easy to test. That is the entire reason those two domains took off with LLMs before everything else — not because they are easier, but because verification is automatable. If you cannot verify the output, you cannot trust the automation.

What to do when a criterion fails

FailingMove
Cost of error is highAdd a human in the loop
Data is poor / output hard to verifyUse AI for augmentation — generate options, human selects
Only verification is hardAutomation is still possible, but requires heavy investment in evaluation

Evaluation — where the real human work lives
🔬
28 · Problem
Why evaluation is genuinely hard
▼
  • Output is probabilistic. Run the same input twice, get two different outputs. There is no fixed answer to diff against.
  • No unit tests. You cannot assert input X always produces output Y, because it does not.
  • The science is unsettled. Google, Anthropic and everyone else use different methods and each claims theirs is best. This is not a solved field you are failing to look up.
The asymmetry to internalize

Building is cheap — Lovable plus n8n produces a working agent in hours. Evaluation is expensive, slow, and where most of the real human work lives. Which is exactly why it is 20% of the project grade and why it is the component teams under-invest in.

🏥
29 · Case
The healthcare CRM case — Alex Lee as gold standard
▼

The setup

A medical-device sales company. Reps — Jordan, Marcus, Dana and others — resist entering data into the CRM after sales calls. Five agent prototypes were built to write the follow-up for them: Agent Leopard, Agent Rhino, Agent Macaw, Agent Eagle, Agent Crocodile.

The gold standard

Alex Lee is the meticulous rep — detail-oriented, and only a few months into the job, so still diligent about CRM entries. His outputs are the benchmark. Note why he is the benchmark: not seniority, but observable, consistent, high-quality output you can copy the shape of.

The data you get

  • 5 samples of Alex's actual conversations, plus his summaries, next steps and follow-up emails.
  • 5 tabs of agent output — one per prototype — with subject lines and email bodies.

That is the whole evaluation problem in miniature: a small set of expert examples, and a pile of candidate outputs to rank against them.

⚖️
30 · Method
Human eval vs. LLM-as-judge
▼
Human evaluation Show the outputs to Alex and have him score them against his own standard. + ground truth from the domain expert. − slow, expensive, does not scale.
LLM-as-judge (digital twin) Build an n8n agent that holds Alex's data as the gold standard and have it evaluate every prototype's output against his style and content. Scales; needs to be built carefully.

How the judge was built

  1. Ask the LLM: “If I want to create a follow-up email like Alex, what should my system message be?” → it produces detailed explicit rules — always end with “Warm regards”, use this structure, keep it concise, and so on. The gold standard gets turned into a written rubric by the model itself.
  2. Feed the judge both the derived system prompt and Alex's sample data.
  3. Ask it to rank all five prototypes.
Result in the demo

Macaw and Eagle ranked highest — consistent with the human evaluation, though not identical to it. “Consistent but not identical” is roughly the state of the art, and worth saying out loud in your video.

The failure mode he demonstrated live

On the first run the judge did not use Alex's data at all — visible as no green check mark on the tool call in the execution log. It had to be told explicitly to “always use Alex Lee's data as the gold standard.” Always verify tool use in the execution log. If the agent did not call the tool, the output is worthless no matter how good it reads.

31 · Rubric
Evaluation criteria and the improvement loop
▼

What to score on

CriterionThe question it asks
AccuracyDoes the content match what was actually discussed?
RelevanceIs the output appropriate to the context?
ExplainabilityCan you tell why it said what it said? Especially important in regulated industries.
Tone & styleDoes it match the intended persona?
StructureSubject line, greeting, sign-off — does it follow the required format?
CompletenessAre all required fields populated?

The loop

  1. Baseline agent — minimal system prompt, just the data.
  2. Evaluate against the gold standard.
  3. Identify failure modes — wrong tone, missing fields, hallucinated details.
  4. Update the system prompt with explicit rules aimed at those failures.
  5. Re-evaluate. Repeat.
This is the deliverable

This loop, documented, is component 3 of the project grade. Keep the baseline output. Keep the failure list. Keep the prompt diffs. The before/after is the evidence — a claim that you “iterated” with nothing to show is worth nothing.

32 · Guardrails
HIPAA, and designing around the objection
▼

Recording sales conversations in healthcare is a HIPAA risk: a rep can mention a patient's condition in passing and now you have protected health information in a recording.

The design move

Record an after-the-fact memo instead of the live conversation. The rep dictates a summary after the call. Two things happen at once: you stop capturing PHI, and Jordan gets more comfortable with adoption. The privacy fix and the adoption fix are the same change.

Stacked guardrails

  • Transcription guardrail — instruct the agent to strip personal health information before storing.
  • Enterprise environment — use enterprise-grade cloud, not personal ChatGPT accounts.
The inversion worth stealing

Reps are already pasting call notes into personal ChatGPT accounts — that is live data leakage happening today. So a proper deployment centralizes the data and gives the company control over where it sits. It answers Morgan's data-governance objection as an improvement, not a new risk. When someone raises governance, check what the unmanaged status quo already leaks.

33 · Strategy
The paradox of access, and where moats come from
▼
The paradox

AI improves productivity for everyone — and if everyone has the same models, prices fall and the gains go to customers, not companies. Economics 101: commoditized tools create no competitive advantage. Deploying agents your competitors also deploy lowers cost and price industry-wide. Good for society, neutral-to-negative for shareholders.

The bottom tiers of intelligence — high-school-level tasks — are already commoditized, with American and Chinese models competing hard on price.

So where does advantage come from? Scarcity.

MoatExample
Proprietary weightsAnthropic's current position — others cannot replicate what the model does.
Proprietary dataData your competitors simply do not have.
Network effectsTwo-sided platforms — Uber (drivers + riders), Google (consumers + advertisers).
Speed of executionSmall and nimble ships faster than an incumbent with more approval layers.

The last fifty years of tech is largely one playbook run repeatedly: build a societal platform with network effects. (Plug-and-play model switching and the pricing pressure it creates: deferred to Lecture 3.)

34 · Adoption
Change management — the $1 : $4 rule
▼
The number to remember

For every $1 spent on software, expect to spend $4 on change management. From AI-transformation leaders at McKinsey and peers.

Adoption is hard, and people resist for valid reasons — job security, HIPAA, distrust of AI accuracy. The response is not to dismiss the objection:

  1. Understand it through conversation.
  2. Design a guardrail that addresses it — after-the-fact memos instead of live recording.
  3. Quantify the upside — post-call admin from 15 minutes down to 5 per rep.
  4. Show the governance improvement against the ad-hoc personal-ChatGPT status quo.
The strategic vulnerability

If you do not automate and a lean competitor builds an agentic version of your business from scratch, you are in a very difficult position. Lobel's line on what actually keeps CEOs and CFOs up: “a 28-year-old with a Lovable account” building a competitor that moves 10× faster.

The balance he ended on: AI makes mistakes, and humans sometimes do better — but the competitive risk of inaction is real, and it is the risk that does not show up on anyone's dashboard.

Every idea from the session, sorted by which 20% it earns you.

1 · Problem & value proposition

  1. Pick from your own domain expertise — you cannot argue a problem matters if it is not yours.
  2. Run it through the 2×2: high ambiguity + low cost of error is the agent sweet spot; two of the four boxes say don't build an agent.
  3. Frame it as a process, not a project — name the trigger or the schedule.
  4. Apply the three criteria: low cost of error, clean data, easy to verify — and say which one is weakest and what you did about it.
  5. Quantify the upside the way the class exercise did: hours per week, salaries, 15 minutes → 5.

2 · Agent design

  1. Automation / augmentation / hybrid — state which archetype and why.
  2. Human in the loop = guardrail vs. bottleneck. Say where you put the line and what it costs.
  3. System prompt under Options, never in the prompt input field.
  4. List every tool explicitly in the system prompt — it measurably improves tool selection.
  5. Expression fields are what make a tool general instead of hardcoded.
  6. Orchestration is the lever for managing stochasticity — more structure where errors are costly.
  7. Header auth on the webhook; password collected at runtime, never hardcoded in the frontend.

3 · Evaluation

  1. Name a gold standard — a person, or a set of known-good outputs. Alex Lee is the pattern.
  2. Derive the rubric from the gold standard by asking the model what system prompt would reproduce it.
  3. LLM-as-judge for scale, human eval for ground truth — the demo used both and they agreed roughly, not exactly.
  4. Verify the judge actually called its tools — the green check in the execution log.
  5. Six criteria: accuracy, relevance, explainability, tone, structure, completeness.
  6. Show the loop with receipts: baseline → failure modes → prompt change → re-evaluation.

4 · Presentation

  1. Confirm the runtime — today's brief said 5 minutes, the earlier spec said 8.
  2. Text in, text out. No image or video inputs.
  3. Say the honest limits out loud — what the agent is bad at is a graded question, not an admission.
